# Codex Prompt — QRUnlock Smart RF Door-Lock Power Supply Firmware

You are implementing **production firmware only** for a QRUnlock smart electronic-door-lock power-supply controller.

This is a real commercial product intended for long-term deployment and eventual integration into the **ONE IoT Platform**.

Work efficiently. Avoid unnecessary refactoring, over-engineering, long explanations, generated documentation, or speculative features. Complete one working firmware deliverable.

## 1. Hardware

MCU:

* ESP32-C3 Super Mini
* ESP-IDF preferred unless the existing repository already uses another established ESP32 framework
* Wi-Fi required
* BLE may be used for provisioning only if already supported cleanly by the existing architecture

RF receiver:

* RX480-E-WQ or compatible learning RF receiver
* RF remote operates the door-lock relay

GPIO requirements:

### GPIO3 — Relay Control

* GPIO3 = relay command output
* Active HIGH
* GPIO3 HIGH must switch an NPN transistor
* transistor drives relay coil
* proposed base resistor = 330 O
* firmware must initialize GPIO3 LOW before normal startup
* relay must NEVER pulse accidentally during:

  * boot
  * reset
  * OTA
  * Wi-Fi provisioning
  * watchdog restart
  * brownout recovery

Use a configurable relay pulse duration.

Default:

`1000 ms`

Allow safe configuration range:

`200–5000 ms`

Never allow relay to remain ON indefinitely because of firmware failure.

## 2. GPIO2 — RF VT / Learning Interface

GPIO2 needs special treatment.

Desired behavior:

### Normal mode

GPIO2 should monitor the RF receiver VT signal.

When a valid learned RF remote is received:

`VT -> HIGH`

Firmware detects the HIGH signal and activates the relay.

Use debounce / minimum valid pulse filtering so noise cannot unlock the door.

### RF-learning mode

The current hardware concept requires ESP32 GPIO2 to temporarily provide a HIGH signal for approximately 10 seconds to place the RF module into learning mode.

During this learning window:

1. trigger RF learning mode
2. wait for a remote transmission
3. detect confirmation / VT state change
4. determine whether remote learning succeeded
5. stop learning immediately after success
6. otherwise timeout after 10 seconds
7. return GPIO2 safely to input-monitoring mode

### IMPORTANT ELECTRICAL VALIDATION

Do NOT blindly configure GPIO2 as push-pull HIGH while it is directly connected to an output pin of the RF receiver.

First inspect the RX480-E-WQ interface assumptions and determine whether VT is:

* push-pull output
* open collector
* open drain
* internally pulled
* bidirectional
* or whether a different LEARN pin is actually intended

Avoid GPIO output contention.

Prefer a safe implementation such as:

* open-drain drive where electrically valid
* input mode during normal RF monitoring
* carefully controlled direction switching
* transistor/diode isolation recommendation if required

If the proposed single-wire design is electrically unsafe, DO NOT fake a software solution.

Instead:

1. implement the safest firmware abstraction possible
2. document the exact minimal hardware correction required
3. keep the firmware API compatible with the intended behavior

Do not change GPIO assignments unnecessarily.

## 4. GPIO6 — Multifunction Button

GPIO6 = physical multifunction button input.

Use appropriate pull-up/pull-down according to hardware.

Required actions:

### Short press

Do not erase configuration.

Can be reserved for local status/action if useful.

### Provisioning press

Provide behavior similar to common Tuya devices.

For example:

hold approximately 5 seconds:

* enter provisioning/AP mode
* indicate provisioning mode through LED

### Factory reset

Longer hold, for example approximately 10 seconds:

* erase Wi-Fi credentials
* erase ONE IoT binding/configuration
* retain immutable manufacturing identity
* reboot into provisioning mode

Protect against accidental factory reset.

Use state-machine/timer logic, not blocking delays.
