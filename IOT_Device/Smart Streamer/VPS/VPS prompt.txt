# CODEX IMPLEMENTATION PROMPT

## JENIX SMART STREAMER — MULTI-TENANT VPS CONTROL PLANE

You are working on a production-grade commercial product named **Jenix Smart Streamer**.

Develop the VPS-side control-plane service for onboarding customers, registering ESP32-P4 Smart Streamer devices, managing cameras, storing streaming destinations, managing schedules, authorizing stream sessions, and receiving device health telemetry.

This is not a prototype, hobby project, demonstration project, or child-level implementation. Build it as a maintainable sellable product intended to remain operational for at least 10 years.

---

# 1. PRODUCT BEHAVIOUR

A customer may own multiple ESP32-P4 Smart Streamer devices.

Each P4 device:

* Is assigned to one customer or tenant.
* Connects to one IP CCTV camera at a time.
* Can stream to YouTube, Facebook, or Instagram.
* Can stream to only one destination at a time.
* Sends video directly to the selected platform.
* Never sends video through the VPS.
* Uses the VPS only for authentication, configuration, schedules, destination credentials, status, and orchestration.

A single customer may run multiple simultaneous live streams by using multiple P4 devices.

Example:

```text
Customer A
+-- P4-01 ? Camera 01 ? YouTube
+-- P4-02 ? Camera 02 ? Facebook
+-- P4-03 ? Camera 03 ? Instagram
```

Enforce:

```text
Maximum active stream per P4 device = 1
Maximum assigned active camera per device = 1
Maximum destination per stream session = 1
```

---

# 2. CRITICAL ARCHITECTURE RULE

The VPS is a lightweight control plane only.

It must never:

* Receive RTSP video.
* Proxy RTMP or RTMPS video.
* Buffer H.264 data.
* Record video.
* Transcode audio or video.
* Accept video file uploads through the stream-control APIs.
* Act as a media relay.

Video flow must remain:

```text
IP CCTV Camera
      ¦ RTSP
      ?
ESP32-P4
      ¦ RTMPS
      ?
YouTube / Facebook / Instagram
```

Control flow:

```text
ESP32-P4
      ¦ HTTPS JSON
      ?
Jenix VPS Control Plane
```

Reject unsupported binary or oversized payloads.

---

# 3. RESOURCE TARGET

Target VPS:

```text
Linux VPS
1 vCPU
512 MB RAM
Fixed DNS endpoint
```

Resource objectives:

* Idle application memory target: below 50 MB where reasonably possible.
* Active normal operation target: below 120 MB.
* Do not require Redis.
* Do not require RabbitMQ.
* Do not require Kafka.
* Do not use Kubernetes.
* Do not use PostgreSQL for the first low-resource release unless the existing repository already depends on it.
* Prefer SQLite in WAL mode for the first production deployment.
* Keep migration support so PostgreSQL can be introduced later.
* Do not create one operating-system thread per device.
* Do not maintain permanent WebSocket connections unless already required by the platform.
* Prefer device polling with randomized intervals for the initial release.
* Avoid unnecessary third-party packages.

Use:

* Python 3.12 or currently supported stable Python version in the repository.
* FastAPI.
* Uvicorn.
* Pydantic.
* SQLite WAL.
* Async database access.
* Caddy or Nginx for TLS termination.
* systemd for process supervision.

Start with one Uvicorn worker on a 512 MB server.

Do not blindly create two or more workers because each worker duplicates application memory and in-memory state.

Do not create a duplicate customer login system when integrating with Jenix One.

Implement an authentication adapter that can:

* Validate the existing Jenix One access token or JWT.

* Read the tenant, organization, or customer ID.

# 7. USER AND DEVICE ONBOARDING

Implement a secure device-claim workflow.

Suggested flow:

1. Manufacturing assigns:

   * Hardware serial number.
   * Product ID.
   * Device ID.
   * Device bootstrap secret or device certificate.

2. P4 device completes universal Jenix provisioning.

3. Device contacts VPS using its bootstrap identity.

4. VPS creates a short-lived claim token or claim code.

5. Authenticated Jenix One user selects “Add Smart Streamer”.

6. User enters or scans the claim code.

7. VPS atomically assigns the device to the user’s tenant.

8. Device bootstrap credentials are rotated or upgraded to permanent device credentials.

9. Claim token becomes unusable.

Requirements:

* Claim tokens must expire.
* Claim tokens must be single-use.
* Claim attempts must be rate-limited.
* A claimed device cannot be silently claimed by another tenant.
* Device transfer must require an explicit administrative release or factory-reset workflow.
* Log every claim, release, revoke, and credential rotation operation.

# 8. DEVICE AUTHENTICATION

Do not use a permanent plain `X-Access-Key` as the only device-security mechanism.

Implement request signing.

Recommended headers:

```http
X-Device-ID: JNX-P4-000101
X-Timestamp: 1785684320
X-Nonce: random-unique-value
X-Signature: base64-hmac-sha256
```

Signature input must include:

```text
HTTP method
request path
timestamp
nonce
SHA-256 request-body hash
```

Requirements:

* Reject timestamps outside the allowed clock window.
* Reject reused nonces.
* Use constant-time signature comparison.
* Support credential rotation.
* Support device revocation.
* Do not log raw signatures or secrets.
* Enforce HTTPS.
* Allow a controlled time-synchronization recovery flow for devices with invalid clocks after prolonged power failure.
* Add replay-protection tests.

Design the authentication interface so hardware-backed certificates can be supported later.

# 9. SECRET STORAGE

Encrypt sensitive fields at rest:

* RTSP camera passwords.
* YouTube stream keys.
* Facebook stream keys.
* Instagram temporary stream keys.
* OAuth refresh tokens.
* Platform account references.

Use authenticated encryption such as AES-GCM through a well-maintained library.

The master encryption key must:

* Come from an environment secret or protected secret file.
* Never be committed to Git.
* Never be printed in logs.
* Support future key rotation.

Do not store browser cookies for Instagram.

Do not ask customers for social-platform account passwords.

# 11. SESSION AUTHORIZATION

Implement an atomic device-session lock.

A device may have only one active or starting session.

Session states:

```text
REQUESTED
AUTHORIZED
DEVICE_CONNECTING
STREAMING
STOP_REQUESTED
STOPPING
STOPPED
FAILED
EXPIRED
```

When a second start request is made for a busy device, return:

```http
409 Conflict
```

Example:

```json
{
  "error": {
    "code": "DEVICE_ALREADY_STREAMING",
    "active_session_id": "SES-20260803-0012",
    "active_platform": "youtube"
  }
}
```

Also implement an optional destination lock to prevent two P4 devices from accidentally using the same destination stream key.

All session state transitions must be validated.

Do not allow impossible transitions such as:

```text
STOPPED ? STREAMING
FAILED ? STREAMING
```

without creating a new session.

# 13. SCHEDULE MANAGEMENT

Support:

* Timezone per schedule.
* Default timezone `Asia/Kolkata`.
* Day-of-week recurrence.
* One-time events.
* Date range.
* Enabled or disabled status.
* Manual start and stop.
* Schedule priority.
* Overlap validation.
* Missed-event policy.
* Early-start and late-stop tolerances.

Every schedule must identify:

```text
device_id
camera_id
destination_id
timezone
start time
stop time
```

Reject overlapping active schedules for the same P4 device.

The VPS must not independently create thousands of simultaneous heavy jobs.

Prefer one of these low-resource designs:

1. Devices periodically fetch their next schedule using randomized polling.
2. Maintain a compact in-memory min-heap of upcoming control events rebuilt from SQLite.
3. Combine both, with device polling as the reliability fallback.

Do not use one thread or one timer per schedule.

# 14. POWER-CUT AND THUNDERING-HERD PROTECTION

After a widespread power failure, many P4 devices may reboot simultaneously.

Design the server and API so this does not overload the VPS.

Requirements:

* Firmware applies randomized startup delay.
* Server supports `Retry-After`.
* Rate-limit per device and per IP.
* Use bounded request queues.
* Keep request processing short.
* Avoid database table scans on every device poll.
* Add indexes for device ID, tenant ID, session state, schedule time, and last-seen time.
* Cache only non-sensitive, bounded data.
* Do not hold database transactions while calling external APIs.
* Use idempotency keys for session-start requests.

Return controlled responses:

```http
429 Too Many Requests
Retry-After: 37
```

or:

```http
503 Service Unavailable
Retry-After: 45
```

Never allow all devices to retry at exactly the same fixed interval.

# 16. RATE LIMITING

Implement low-memory token-bucket or sliding-window limits.

At minimum:

* Device bootstrap rate.
* Device claim rate.
* User login adapter rate.
* Session authorization rate.
* Heartbeat rate.
* Invalid-signature rate.
* Platform credential validation rate.

Because the initial deployment uses one application worker, a bounded in-memory limiter is acceptable for fast-path protection.

Security-critical claim attempts and failed authentication counts should also be persisted or audit-logged.

Do not allow unbounded dictionaries that grow forever.

Implement expiry cleanup.

---

# 17. EXTERNAL API CALLS

When calling YouTube or future Facebook APIs:

* Use one shared asynchronous HTTP client.
* Configure connection pooling.
* Set strict timeouts.
* Set response-size limits where possible.
* Retry only idempotent or explicitly safe operations.
* Use exponential backoff with jitter.
* Do not retry authentication failures indefinitely.
* Use circuit-breaker behaviour.
* Never hold a SQLite write transaction while waiting for an external API.
* Preserve the original meaningful HTTP error instead of converting all errors to status 500.

Do not use broad exception handling that accidentally swallows framework HTTP exceptions.

# 24. FAILURE BEHAVIOUR

The system must fail safely.

Examples:

* If the database is unavailable, do not authorize a new stream using guessed data.
* If destination credentials are expired, return a clear error.
* If an external API is unavailable, preserve existing reusable credentials where safe.
* If the server restarts, active session records must remain recoverable.
* If a device repeats an idempotent request, return the original session result where valid.
* If time synchronization is temporarily invalid after power restoration, use the defined recovery process rather than disabling security globally.

# 27. DEFINITION OF DONE

The implementation is complete only when:

* A Jenix One user can claim multiple P4 devices.
* Tenant isolation is tested.
* Each device can be assigned one camera.
* YouTube, Facebook, and Instagram destination profiles can be stored securely.
* A P4 can authorize only one active stream at a time.
* Multiple P4 devices owned by one customer can stream concurrently.
* Scheduling works with `Asia/Kolkata` as the default timezone.
* Overlapping schedules for the same device are rejected.
* Device credentials are signed, replay-protected, revocable, and rotatable.

* The service runs on a 1-vCPU, 512-MB VPS.
* Reconnection bursts are controlled.
* All maintained source files remain under 200 lines.
* Tests pass.
* Deployment, backup, restore, upgrade, and rollback instructions are present.
