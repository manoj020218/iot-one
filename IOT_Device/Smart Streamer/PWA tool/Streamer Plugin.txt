# CODEX IMPLEMENTATION PROMPT

## JENIX ONE IOT PLATFORM PLUGIN — SMART STREAMER

Develop a production-grade plugin for the existing **Jenix One IoT Platform** named:

```text
Smart Streamer
```

The plugin manages ESP32-P4 devices that stream an IP CCTV camera directly to:

```text
YouTube
Facebook
Instagram
```

Each P4 device supports:

```text
One camera
One destination
One active stream
at one time
```

A single Jenix One customer may own and manage multiple Smart Streamer devices.

Multiple devices owned by one customer may stream simultaneously.

The plugin must use the existing Jenix One:

* User login.
* Tenant model.
* Role model.
* Multi-device user flow.
* Device registry.
* Product ID system.
* OTA system.
* Audit logging.
* Notification framework.
* Plugin architecture.
* Universal provisioning flow.

Do not create a separate application, separate login, separate user database, or duplicate provisioning experience.

---

# 13. POWER-CUT RECOVERY STATUS

The UI must explain device recovery after power restoration.

Display states such as:

```text
Reconnecting after power restoration
Waiting for time synchronization
Startup delay active
Fetching current schedule
Resuming eligible live session
Schedule window already ended
```

Show the randomized delay as a normal protective behaviour, not as an error.

Suggested message:

> The device is delaying reconnection briefly to prevent all deployed Smart Streamers from contacting the server simultaneously after a power outage.

Do not allow the UI to force every offline device to reconnect at exactly the same moment.

# 18. SECURITY AND PRIVACY

Requirements:

* Never store secrets in browser localStorage.
* Prefer secure server-side storage.
* Use existing access-token handling.
* Mask camera and platform credentials.
* Do not include secrets in analytics.
* Do not include secrets in error reports.
* Use CSRF protection where required by the existing authentication design.
* Use tenant-isolated API calls.
* Sanitize user-entered labels.
* Confirm destructive actions.
* Apply rate limiting to credential validation.
* Audit secret changes without recording secret values.
* Automatically clear sensitive form state after save or cancel.

* Server state.

* Local UI state.

# 25. STATUS REFRESH

Use adaptive polling rather than aggressive constant polling.

Suggested behaviour:

```text
Overview visible: moderate polling
Device detail visible: faster polling
Live-session page: 10–30 second polling
Background tab: reduced polling
App hidden: pause or greatly reduce
Offline device: slow polling
```

Apply randomized jitter.

Do not make every browser request status at the same exact interval.

Reuse existing realtime capability if Jenix One already has a lightweight working mechanism.

# 31. DEFINITION OF DONE

The Smart Streamer plugin is complete only when:

* It appears as a native Jenix One plugin.
* Existing Jenix One login is reused.
* Existing tenant and role flows are reused.
* Universal provisioning is reused.
* A user can claim multiple P4 devices.
* Each P4 has an independent device page.
* A camera can be configured and tested.
* YouTube, Facebook, and Instagram destinations can be configured.
* Credentials are masked and securely handled.
* One device can run only one active stream.
* Multiple devices can stream simultaneously.
* Schedules support `Asia/Kolkata`.
* Schedule conflicts are detected.
* Power-cut recovery status is visible.
* Device diagnostics are available.
* OTA uses the existing Jenix One framework.
* All actions are permission-controlled and audited.
* Mobile PWA and Capacitor layouts work.
* All maintained source files remain under 200 lines.
* Automated tests pass.
* Documentation is complete.
